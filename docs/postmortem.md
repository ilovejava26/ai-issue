## 근본 원인

Spearman은 순위로 변환한 뒤 Pearson을 계산한다.
pairwise 결측치 제거는 **`x`와 `y` 중 하나라도 결측인 행을 모두 제거**해야 한다.

```python
# 문제가 된 코드
mask = ~np.isnan(x)
x_rank = rank(x[mask])
y_rank = rank(y[mask])  # y의 NaN이 남아 있음
return pearson(x_rank, y_rank)
```

`y`에 남은 `NaN`은 `argsort`에서 가장 큰 값처럼 정렬되어 순위가 부여되었고, 결과적으로 `NaN`이 아니라 **틀린 숫자**가 반환되었다.
`NaN`이 그대로 전파되었다면 오히려 빨리 발견했을 수 있었지만, "그럴듯한 값"이 나와 탐지가 지연되었다.

### 5 Whys

1. **왜 틀린 값이 나왔나?** `y`의 결측치가 제거되지 않은 채 순위가 매겨졌기 때문이다.
2. **왜 제거되지 않았나?** pairwise 마스크를 `x`에만 적용했기 때문이다.
3. **왜 `x`에만 적용했나?** Pearson 구현을 재사용하면서 "결측치 위치는 항상 같다"고 가정했기 때문이다.
4. **왜 테스트가 잡지 못했나?** `NaN`을 `x`에만 넣은 케이스와 완전한 데이터만 테스트했기 때문이다.
5. **왜 그 조합만 테스트했나?** DoD의 "경계값 테스트"가 결측치의 **위치 조합**까지 요구하지 않았고, 리뷰도 API 형태에 집중했기 때문이다.

## 배운 점

- **결측치는 "값"이 아니라 "위치"가 문제다.** `NaN`이 있는지만 보지 말고, 어느 배열의 어느 위치에 있는지 조합으로 검증해야 한다.
- **SciPy 대조 테스트도 입력이 다양해야 의미가 있다.** 정상 데이터만 비교하면 경계값 버그를 놓친다.
- **틀린 값은 `NaN`보다 위험하다.** `NaN`은 즉시 눈에 띄지만, 그럴듯한 숫자는 조용히 의사결정을 오염시킨다.
- **릴리스 후 24시간은 실제 사용자 입력으로 검증하는 시간이 필요하다.** 소스 트리 테스트와 배포 산출물, 실제 데이터는 다르다.
